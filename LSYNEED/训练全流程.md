## 1. 实验合同（写脚本之前读完）

这些数字写在最终 proposal 里，主结果必须照做。为了 loss 更好看去改它们，实验就作废。

| 项目 | 锁定值 |
|---|---|
| 基座 | `Qwen/Qwen2.5-0.5B`（Base，不是 Instruct），revision `060db6499f32faf8b98477b0a26969ef7d8b9987` |
| 方法 | LoRA，r = 32，alpha = 64 |
| SFT 学习率 | 1e-4 |
| DPO 学习率 | 5e-6 |
| DPO beta | 0.1 |
| 每个阶段的 epoch | 正好 1 |
| 种子 | 42、1337、2024。10,000 档只用 42。M0 只用 42 |
| TL;DR `max_length` | 1024 |
| M0 `max_length` | 2048 |
| SFT loss | 只计算 assistant 回复和结尾的 `<\|im_end\|>` |
| 两阶段之间 | 把 LoRA 合并进基座，下一阶段用全新优化器和新的 LoRA |

Tokenizer 每次加载都执行：

```python
tokenizer.eos_token = "<|im_end|>"       # id 151645
tokenizer.pad_token = "<|endoftext|>"    # id 151643
tokenizer.padding_side = "right"         # 训练用 right；生成评测才用 left
```

`pad_token` 和 `eos_token` 必须是两个不同的 token。设成同一个，模型学不会停止。

谁从哪份权重开始：

| 臂 | 在做什么 | 起点 | DPO 的冻住参考模型 |
|---|---|---|---|
| M0 | 5,000 条通用指令 SFT，1 epoch | 原始 Base | 无 |
| G2 | 纯 SFT，用 N 条 chosen | M0 | 无 |
| G3 | 纯 DPO，用 N 对偏好 | M0 | M0 |
| G4 stage1 | SFT，part A（0.5N） | M0 | 无 |
| G4 stage2 | DPO，part B（0.5N） | G4 stage1 合并后的模型 | 同一份 stage1 合并模型 |
| G5 stage1 | DPO，part B（0.5N） | M0 | M0 |
| G5 stage2 | SFT，part A（0.5N） | G5 stage1 合并后的模型 | 无 |
| G3′ | 冷启动 DPO，只有 500、种子 42 | 原始 Base | 原始 Base |

G4 和 G5 在同一预算下看到的句子是同一批，只是阶段顺序相反。这是整篇项目要回答的问题。

DPO 如果出现 NaN 或 loss 爆掉：所有 DPO run 一起改成学习率 `1e-6`、beta `0.3`，已经训完的 DPO 用新设定重跑，并在 README 写明「偏离预注册，使用 proposal 里的发散预案」。不要只改其中一条。

下面这些 proposal 没有锁。选定之后写进每一份 config，44 次全部相同。显存不够时，只允许减小 `per_device_train_batch_size`、同时增大 `gradient_accumulation_steps`，让两者的乘积保持 16。

| 工程默认 | 值 |
|---|---|
| 精度 | bf16（卡不支持 bf16 再用 fp16） |
| 等效 batch | 16（例如 per-device 4 × 累积 4） |
| 优化器 | AdamW |
| 学习率日程 | cosine，warmup_ratio 0.03 |
| 梯度裁剪 | 1.0 |
| LoRA dropout | 0.05 |
| LoRA 目标层 | `q_proj,k_proj,v_proj,o_proj,gate_proj,up_proj,down_proj` |
| 最后不满一个 batch | 保留，`dataloader_drop_last=false` |
| 预期步数 | `ceil(样本数 / 16)`，因为 epoch = 1 |

500 档每个阶段大约十几到三十几步。这是提案已经接受的情况。主结果仍然只训 1 个 epoch。不要把主表改成 3 个 epoch。

### 步骤 C — 写一个脚本，覆盖全部 44 次

脚本放在 `LSYNEED/training/`。checkpoint 只写到 `03_runs/`。不要往 `01_data/` 写任何东西。

需要的文件：

| 文件 | 作用 |
|---|---|
| `train_sft.py` | 读 SFT jsonl 的 `messages`，`assistant_only_loss=True`，训 1 epoch，保存 LoRA |
| `train_dpo.py` | 读 `prompt` / `chosen` / `rejected`，加载一份冻住的 ref，训 1 epoch，保存 LoRA |
| `merge_lora.py` | 把 adapter 合并进当时的起点模型，存成完整模型 |
| `make_configs.py` | 按第 7 节的表生成 44 份 yaml，避免手改 |
| `configs/*.yaml` | 每个 run 一份，原样复制进该 run 目录 |

SFT 数据字段用 `messages`。DPO 三个字段都是对话列表，不要改成纯字符串。

DPO 的参考模型是另一份加载出来的冻住权重，和正在训练的 LoRA 模型不共享参数。

两阶段的做法：

1. stage1 从指定起点训练，保存 adapter。
2. `merge_lora.py` 写出 `checkpoint/merged/`。
3. stage2 的 yaml 里，`model_path` 指向这份 merged。优化器是新 Trainer 自己的，不要把 stage1 的 optimizer 文件拷过去。
4. stage2 再合并一次，最终评测加载 stage2 的 merged。

每份 yaml 至少包含：臂名、阶段、预算、种子、数据文件的绝对路径、起点模型路径、DPO 参考模型路径、上面第 1 节的全部超参、数据版本 `v1.0`、输出目录。

训练开始前，脚本对 1 条样本打印 `(token_id, token 文本, label)`。SFT 里 system 和 user 的 label 是 `-100`，assistant 正文和结尾 `<|im_end|>` 的 label 是真实 token id。这条打印写进 `train.log` 的开头。

种子要设到 Python、NumPy、PyTorch 和 Trainer 的 `seed`。同一份代码、同一个种子、同一个数据文件，重跑应得到同一条训练曲线。

日志：`report_to=none`，`logging_steps=1`，只在 epoch 结束时保存，避免中间 checkpoint 撑满磁盘。

## 5. 卡住时对照

| 现象 | 处理 |
|---|---|
| loss 是 NaN，或 DPO 曲线突然飞掉 | 全部 DPO 改用 lr `1e-6`、beta `0.3`，重跑 DPO 阶段，README 记录预案 |
| CUDA out of memory | 减小 per-device batch，增大累积步数，乘积保持 16。先对 M0 和 DPO 这样做 |
| 生成停不下来，或一直输出 pad | 检查 eos 是 151645、pad 是 151643，两者不同 |
| stage2 的 loss 和 stage1 几乎同一条曲线 | 检查 stage2 的 `model_path` 是不是 stage1 merged，而不是 M0 |
| 步数比 `ceil(n/16)` 少很多 | 检查有没有把 epoch 设错、有没有 `drop_last`、有没有拿错预算的文件 |
| 想覆盖一个已经写好的 run | 新开 `_rerun1` 或新日期目录 |
