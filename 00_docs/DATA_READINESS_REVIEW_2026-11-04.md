## 1. 我对 proposal 的理解

研究对象是 Qwen2.5-0.5B 的后训练顺序：在共享的通用指令预热模型 M0 上，比较 SFT→DPO 与 DPO→SFT，并观察顺序优势 OA(N) 在 500、2,000、10,000 个唯一 prompt 预算下如何变化。

- G2：N 条 chosen 做 SFT；G3：N 个偏好对做 DPO。
- G4：A 集 N/2 条 chosen 做 SFT，再用 B 集 N/2 个偏好对做 DPO。
- G5：先用同一 B 集做 DPO，再用同一 A 集做 SFT。
- G3′：裸 Base 上做 500 对 DPO，作为冷启动对照。
- 500/2k 各三个种子，10k 一个种子；主测试集为 200 个 TL;DR prompt。
- 主要终点是各臂相对 M0 的长度受控胜率；MMLU/ARC 衡量能力税，IFEval 检查指令遵循。

因此，数据验收需要分别回答两件事：固定 N 时是否能公平比较顺序，以及改变 N 时是否只增加数据量、没有系统改变偏好样本构成。当前第一项满足，第二项存在缺陷。

## 3. 正式实验前最需要解决的事项

### A. 跨预算负例来源严重漂移，会影响 H2/H3 的规模归因

以下比例从实际 `splits/pool_*.jsonl` 重新统计：

| rejected 来源 | N=500 | N=2,000 | N=10,000 |
|---|---:|---:|---:|
| 人类参考摘要 `human_ref` | 49.40% | 48.75% | 19.87% |
| RL/BoN 模型 `rl_aligned` | 33.60% | 31.35% | 24.02% |
| 较强 SFT 模型 `sft_strong` | 16.20% | 17.45% | 13.53% |
| 早期 SFT 模型 `sft_early` | **0.80%** | **2.45%** | **42.58%** |
| 标注置信度缺失 | 20.80% | 23.20% | 53.50% |
| 标注置信度低于 3 | 8.20% | 6.90% | 3.54% |

这不是 A/B 不平衡：本次重算三档 A/B 长度 SMD，最大绝对值约 0.051，与原报告相符。但 A/B 同样偏向某类负例，仍然能得到很高的平衡检验 p 值。

代码中可以定位到原因：ZIP 内 `data_engineering/scripts/04_split.py` 第 264–276 行，在每个 subreddit/stratum 内先按 `rej_b` 字典序排序，再为整段列表赋 `(j+0.5)/n_s`。取小预算前缀时会优先取得排在前面的 rejected bucket；中点交错平衡了外层，却没有交错内层的 rejected bucket。

这会使数据规模与负例来源、置信度分布一起变化。**来源变化不直接证明负例难度变化，但足以使纯规模解释不稳健。** 固定 N 的 G4/G5 仍然使用完全相同的数据，可以研究该条件下的顺序差异；OA(500) 与 OA(10k) 的差异则不能干净地只归因于样本量。

建议在 `v1.1` 修正：在完整的 chosen/rejected bucket × 长度 × subreddit 子层内随机哈希排序，再按子层容量比例交错各层，同时保持一对 A/B 为采样单位、三个预算严格嵌套。增加**跨预算** rejected、chosen/rejected 联合来源、置信度缺失及低置信度的比例报告和事先定义的偏移阈值。只检查同预算 A/B 的 p 值不够。修复后重导 splits、arms 和 manifest；若内容未变且重新验证通过，可复用原始 canonical pool、测试集和 warmup，避免不必要的重做。

### B. 现有 SFT 单步测试没有覆盖正式 loss 设置

数据卡和交接文档要求 `assistant_only_loss=True`。但 ZIP 内 `tests/test_data_invariants.py` 第 220–230 行创建 `SFTConfig` 时没有设置此选项，随后也只断言训练步数，没有检查训练器实际 batch 的 labels。

自定义 `utils.tokenize_sft_with_labels()` 做出的 mask 正确，不代表 TRL 原生 `SFTTrainer` 最终使用同一 mask。TRL 还可能自动替换训练模板；具体行为需在锁定环境内核验。官方说明要求 assistant mask 对应模板支持 generation 标记，也说明某些模型模板会自动适配：[TRL SFT Trainer](https://huggingface.co/docs/trl/sft_trainer)。这里判定的是**验证覆盖缺口**，不是断言当前版本必然报错。

应补跑与正式配置一致的单步测试，并检查实际 collator 输出：system/user、assistant 提示头、padding 的 labels 为 -100；assistant 正文和停止标记参与 loss；有效 labels 非空、loss/梯度有限；SFT 和 DPO chosen 的实际 token 序列/监督范围符合协议。warmup 至少覆盖单轮与多轮样本。当前 warmup 有 442 条多轮记录，不能简单只保留最后一轮而不说明。

### C. G4/G5 的 DPO reference 不同，应明确研究口径

协议 §9.2 明确写了：G4 的 DPO ref 为 Stage-1 SFT merged 输出，G5 的 DPO ref 为 M0。这是已记录的配方选择，不是数据错配。但 DPO 目标取决于 reference：[TRL DPO Trainer](https://huggingface.co/docs/trl/dpo_trainer)。因此现设计比较的是“各阶段起点作 reference 的两种顺序配方”，不宜表述为完全相同固定 DPO 目标的单纯交换。

若要更严格隔离顺序，可以在正式实验前明确两组 DPO 都用冻结的 M0 reference；若保留现协议，则保留现配方并收窄结论。改变 reference 属于实验设计变更，应更新协议，不能在训练中自行切换。

## 4. 数据质量与统计解释边界

- 14,192/14,733（96.33%）chosen 在观测到的同题比较中未输过。这里只能称“观测比较中零败”，不一定与所有其他候选都比较过，不能等同于严格 Condorcet winner 或摘要绝对正确。
- 全池 8,505 条（57.73%）置信度缺失，455 条（3.09%）低于 3。协议允许回退，因而不属于格式错误；但“所有标签均高置信”是不成立的。
- chosen 仅约 47.62% 来自人类参考摘要，其余为经人类偏好选择的模型输出。适合本研究的偏好训练定义，但不要把 SFT 数据统称为全部人类撰写的优质答案。
- chosen/rejected 记录的平均 token 数约 36.05/32.08，长度偏置确实存在。LCWR 应实际实现并保存原始胜负、长度及换序结果，不能把“长度控制”理解为保证消除所有偏差。
- 检查未发现 post 内的 TL;DR 标记；完整目标文本作为 post 子串的情况为训练池 15 条、测试全集 1 条、主测试集 0 条。抽取式摘要可能自然出现这种现象，不能仅凭子串就判定泄漏。
- 数据标签的 100 对盲评表已经生成，但目录中没有已完成人工评分和一致性结果；proposal 要求的“模型输出的人类—judge 一致性审查”还需在模型生成后单独完成。
- 200 个主测试 prompt 与 proposal 一致，但不能保证足以检出很小的 OA。三种子不等于 600 个独立 prompt；应保持 G4/G5/M0 在同题上的配对，报告种子层面方向与 prompt 聚类的不确定性。10k 单种子结果仅作描述。若扩展到 500，宜事先定义敏感性分析，避免根据主集边界 p 值决定主张。

## 5. 训练与评测工程仍有哪些缺口

当前 ZIP 主要包含数据构造、校验和 IFEval checker，并没有正式 M0/SFT/DPO/LoRA 两阶段训练入口，也没有完整 LCWR judge、MMLU/ARC likelihood 评分及 bootstrap/McNemar 管线。`03_runs` 没有实际训练输出。因此“数据具备输入条件”和“整个项目已经能一键训练评测”需要分别验收。

另外，ZIP 内路径默认是 `PROJECT_ROOT/data/v1.0`，共享目录实际为 `01_data/v1.0`；原测试还依赖未随包提供的 `raw_cache`、官方 tokenizer 和原始 parquet。不能解压后直接照文档运行就认为复现完成。应在独立、可写的工作目录配置路径和恢复缓存，再验证；原 `07_validate.py` 会重建 manifest/数据卡，不应直接对冻结目录运行。

正式训练配置还需落地：实际 Hub ID `Qwen/Qwen2.5-0.5B` 及 revision、LoRA 配置与 PEFT 依赖、有效 batch/梯度累积、scheduler/warmup、packing、drop_last、每阶段 optimizer reset、LoRA merge、新阶段 adapter 初始化、DPO reference checkpoint/hash。等 epoch 或等步骤本身不能证明 G2/G3/SFT/DPO 总 FLOPs 相等；G4/G5 应记录每种阶段的样本/有效 token/优化步数以核对控制条件。

预算也要按最终执行矩阵重算：29 是最终实验臂实例数；双阶段展开后约为 43 个任务训练阶段，另有 M0 预热 1 次。若对全部 29 个最终模型、200 题、两个位置各独立调用一次 judge，约需 **11,600 次调用**；仅 500/2k 的 G4/G5 三种子也需约 **4,800 次**。这些按每题每位置单独调用计，不含重试或其他审查；批处理方式可另设计。不能直接把 proposal 的 3,200 次当作整个矩阵的预算。

## 6. 建议的推进顺序

1. 可立即用现有 warmup 和少量现有训练臂样本接通训练、生成、评分，保存实际 token/labels、loss 与输出；这阶段用于管线调试。
2. 优先修复跨预算 rejected 排序问题并发布 `v1.1`；检查跨预算分布、嵌套性和 G4/G5 镜像绑定。
3. 明确 reference 口径并补齐正式设置的训练器集成验证；冻结训练配置和评测分析方案。
4. 先跑 500 档 G4/G5 一个种子与 M0 对照，核对训练稳定性和完整评测链，再展开全部种子及更大预算。

**目前没有必要为“数量不足”重新搜集一批数据。最有价值的工作是修正采样构成、补齐实际训练验证，并把研究结论的归因边界写清楚。**
